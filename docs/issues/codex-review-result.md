### Issue #017 — 回零状态机放在浏览器而不是控制层

**优先级**：高
**类型**：架构
**涉及文件**：`web_control/homing_test.html`、`docs/architecture.md`

**描述**：
当前回零核心逻辑完全在浏览器页面中执行，页面依赖 `SENS:` 上报驱动前端状态机。浏览器刷新、标签页后台节流、串口瞬断或页面脚本异常时，回零过程会失去一致的控制语义。更实际的问题是该页面只连 Arduino，不连继电器，因此未来 Z 轴刹车正式接入后，这个页面本身也无法安全协调 Z 轴回零。

**为什么重要**：
回零是建立全机坐标基准的安全动作，不应该依赖最不稳定的一层 UI。继续把它放在浏览器里，会让树莓派迁移、远程控制和自动流程都缺少稳定控制边界。

**建议方案**：
把回零状态机下沉到固件或树莓派 host service，浏览器只发高层命令并订阅状态。若短期不重构，至少先让回零页接入继电器控制，并增加“失联即停机”的超时联锁。

### Issue #018 — 原点判定只看电平，没有退回后二次慢速找边

**优先级**：高
**类型**：bug
**涉及文件**：`web_control/homing_test.html`

**描述**：
当前回零逻辑是一旦看到原点传感器为触发态就立即停机并判定“已回零”。如果先撞到负限位，则固定反弹 `800ms` 再继续找原点，这个回弹距离既不看传感器释放边沿，也不看当前速度。整个过程没有“快速接近、退回、慢速二次寻边”的重复定位步骤。

**为什么重要**：
对实验设备来说，能回零不等于能稳定回到同一个零点。没有二次慢速找边，原点重复精度会受惯性、页面时序和传感器安装差异影响，后续绝对定位会越来越不可信。

**建议方案**：
采用标准两阶段回零：快速寻找、退回至传感器释放、慢速再次接近并在边沿锁定零点。把固定时间反弹改成基于传感器状态和最大回退距离的流程，同时加入超时和失败码。

### Issue #019 — 未回零的相对步数被当成绝对毫米坐标展示

**优先级**：高
**类型**：安全
**涉及文件**：`firmware/motor_control/motor_control.ino`、`web_control/index.html`、`README.md`

**描述**：
固件上电后把三轴 `position` 直接初始化为 `0`，主控页则无条件把它换算成毫米并画在带 `HOME` 标记的坐标系里。只要板子重启、重新烧录或换电，页面就会把“未知真实位置”显示成“可信的 0 点附近坐标”。当前系统没有 `homed` 状态，也没有“坐标无效”的 UI。

**为什么重要**：
这是典型的“相对计数冒充绝对坐标”。对人工调试还只是误导，对将来的自动流程则会直接演变成撞机和取放位置错误。

**建议方案**：
引入明确的 `homed / unhomed / fault` 状态；未回零前只显示“相对步数”或“坐标无效”，不要显示 HOME 网格。进一步补上机器坐标与工件坐标的区分，并在回零后才允许绝对定位相关操作。

### Issue #020 — 串口命令协议过于简陋，无法支撑自动化和故障恢复

**优先级**：高
**类型**：架构
**涉及文件**：`firmware/motor_control/motor_control.ino`、`README.md`、`docs/architecture.md`

**描述**：
当前协议基本是“两字符即命令”，只有少量零散文本上报，没有帧边界、命令 ID、校验、明确错误码，也没有绝对定位、回零、配置查询、能力发现这类自动化必需语义。它适合手动点动，不适合树莓派接管后的可恢复控制。命令执行成功与否，也缺乏可机器解析的应答结构。

**为什么重要**：
后续一旦要做远程控制、实验编排、断线重连或日志追溯，现有协议会迅速成为系统瓶颈。越晚重构，前端页面和上位机脚本的迁移成本越高。

**建议方案**：
尽快定义 v2 协议，至少覆盖：命令 ID、结果码、错误码、绝对/相对移动、回零、停止、状态快照、能力查询。文本协议也可以，但要有明确帧格式和 ACK 关联，而不是继续扩展零散口令。

### Issue #021 — 教程把“拔 Arduino USB 线”当急停方式，属于不安全操作

**优先级**：高
**类型**：安全
**涉及文件**：`hardware/tutorials/02-电控接线教程.md`

**描述**：
教程明确建议 Z 轴测试时，如果快撞到顶或底，“立刻拔掉 Arduino 的 USB 线”来紧急停止。这会同时切掉控制、状态回报和可能的安全逻辑，却不会形成规范的去扭矩链路；同一段文字又提醒 Z 轴未接刹车时会下滑。这个建议更像“断通讯逃生”，不应该作为正式操作指南中的急停办法。

**为什么重要**：
错误的急停动作会直接塑造组员的操作习惯。真正出事时，大家会优先做文档里写过的动作。

**建议方案**：
把这段改成明确的临时调试风险提示，并把正式急停动作写成“断 24V 负载 / 硬件急停 / ENA 联锁”。若当前硬件急停尚未建好，应在文档里明确标注“系统暂无合格急停链路，仅允许低速、有人值守调试”。

### Issue #022 — README 中 Z 轴刹车接线仍保留已淘汰继电器脚位，和现用方案冲突

**优先级**：高
**类型**：文档
**涉及文件**：`README.md`、`hardware/采购清单.md`、`docs/architecture.md`

**描述**：
`README.md` 里的 Z 轴刹车接线仍然是旧继电器的 13/14/12/9/8/5 脚位描述，而采购清单和架构文档已经切换到 DSTUR-T80 的 `CH2 COM/NO` 方案。两套接法不仅不同，而且电气含义也完全不一样。新组员如果只看 README，极容易按过期方案误接。

**为什么重要**：
刹车回路接错的后果不是“功能没做出来”，而是 Z 轴不释放、长期堵转，或断电时意外下滑。这个风险比一般文档过时更高。

**建议方案**：
把 README 中旧继电器脚位整段删掉，统一为 DSTUR-T80 的接法，并在文首显式注明“正泰继电器方案已废弃”。同时检查所有教程中是否还残留旧方案术语，避免多处文档各说各话。

### Issue #023 — 三个主页面缺少显式断开和释放串口流程

**优先级**：中
**类型**：工程
**涉及文件**：`web_control/index.html`、`web_control/homing_test.html`、`web_control/sensor_test.html`、`README.md`、`docs/troubleshooting.md`

**描述**：
`index.html`、`homing_test.html`、`sensor_test.html` 都只有“连接”没有“断开”，连接后按钮直接禁用，也没有统一的 `reader.cancel()`、`writer.releaseLock()`、`port.close()` 清理流程。仓库文档已经记录了 Web Serial 占口导致上传失败甚至要重启电脑的问题，但页面层面没有任何缓解措施。

**为什么重要**：
这会持续放大开发摩擦，也让“切页面调试”和“重新烧录固件”成本非常高。随着组员增多，这类流程问题会变成高频操作痛点。

**建议方案**：
给三页都补上统一的断开按钮和 `beforeunload` 清理逻辑，并在 UI 上显示端口状态。更进一步，抽出公共串口生命周期模块，让页面不再各自复制一套连接代码。

### Issue #024 — 刹车状态仅按“写入成功”推断，没有真实状态确认

**优先级**：中
**类型**：安全
**涉及文件**：`web_control/index.html`、`docs/architecture.md`

**描述**：
主控页在发送 CH2 开关命令后，只要写串口成功，就把刹车状态改成“已释放”或“已锁定”。页面并不会解析继电器应答，也没有任何物理反馈输入，因此当前显示本质上只是“命令已发出”，不是“状态已确认”。`未连接 -> 就绪` 这类状态文案也会弱化“未知状态”的风险。

**为什么重要**：
Z 轴安全依赖刹车的真实状态，而不是前端猜测的状态。状态判断一旦失真，操作者会在错误前提下进行上下运动。

**建议方案**：
先把“写成功”与“状态确认”区分开，解析继电器回包后再更新状态；若无确认，就保持“未知/待确认”。在状态未知时禁用 Z 轴动作，长期看则应考虑增加刹车反馈信号。

### Issue #025 — 前端控制逻辑三份复制，已经出现行为漂移

**优先级**：中
**类型**：架构
**涉及文件**：`web_control/index.html`、`web_control/homing_test.html`、`web_control/sensor_test.html`

**描述**：
三页分别维护了自己的串口连接、速度初始化、长按转连续、停止、键盘映射和日志实现。现有 `#009` 已经证明这种复制会产生行为分叉，后续再修串口释放、限位提示、Z 轴方向等问题时也会继续三处漂移。维护成本会按页面数量线性增长。

**为什么重要**：
这不是“代码不优雅”，而是会直接制造安全和行为不一致。实验设备控制页不应该让同一个动作在不同页面有不同语义。

**建议方案**：
抽出共享的 `serial.js / motion.js / ui-state.js` 之类公共模块，统一端口生命周期、命令发送、方向映射和状态解析。页面只保留各自特有的视图与流程逻辑。

### Issue #026 — 项目尚未纳入 Git 版本管理，控制变更缺少追溯与回滚

**优先级**：中
**类型**：工程
**涉及文件**：项目根目录、`README.md`

**描述**：
当前工作区不是 Git 仓库，意味着固件、网页和文档的每次改动都缺少标准 diff、回滚点和发布标记。对普通脚本项目这已经不理想，对运动控制和电气接线文档项目则更危险，因为“哪一版代码对应哪一版接线状态”会很快失去可追溯性。多人协作时，这个问题会进一步放大。

**为什么重要**：
没有版本基线，就没有可靠的回退策略；而硬件系统最怕“改了几处，不知道哪一处把机器变坏了”。后续即使加测试，没有版本管理也很难形成稳定开发流程。

**建议方案**：
先初始化 Git，补 `.gitignore`，把当前可运行状态打一个基线 tag。然后用最简单的规则即可：固件、UI、文档一起提交，重要接线或拨码变化必须写进 commit 和 ADR。

### Issue #027 — 24V 配电方案使用杜邦线拆线加“三股拧线法”，长期可靠性不足

**优先级**：中
**类型**：安全
**涉及文件**：`hardware/tutorials/02-电控接线教程.md`、`hardware/采购清单.md`

**描述**：
教程当前推荐把杜邦线剪头、剥皮后，三股铜线拧成一股再直接塞进电源端子给三台驱动器配电。这个方案在“能跑起来”层面可行，但对振动、接触电阻、导线截面积和重复维护都不友好，尤其不适合作为长期实验设备的正式做法。它更像临时样机方案，而不是成机方案。

**为什么重要**：
配电接触不良会表现为间歇掉电、驱动器异常、莫名报警，排查成本极高。机械平台本身有振动，越是这种环境，越不该依赖拧线式分配。

**建议方案**：
改成合适线径的软线加冷压端头，使用端子排或分配块做 24V 星形分配；最好给各驱动器支路单独加保险。文档里应明确区分“临时调试接法”和“长期使用接法”。

### Issue #028 — “树莓派上位机”目前只有架构图，没有实际可迁移的服务边界

**优先级**：中
**类型**：架构
**涉及文件**：`docs/architecture.md`、`README.md`、`web_control/index.html`

**描述**：
架构文档已经画出了“树莓派 + REST API / WebSocket + Python 编排”，但仓库里还没有任何 host-side service 的雏形，现有控制能力都绑在浏览器本地 Web Serial 上。也就是说，从“当前实现”到“目标架构”之间还缺一层关键中间态。没有这层，后续每加一个设备都会继续堆在 HTML 页面里。

**为什么重要**：
树莓派迁移不是把 HTML 复制过去就结束，而是把设备控制权从浏览器转移到受控服务。这个边界不先建立，未来 RS485 模块、日志、权限和配方都会继续散落在前端里。

**建议方案**：
先做最小化 host service，统一管理 Arduino、继电器和未来 RS485 端口，暴露 API 和事件流；浏览器改成薄客户端。哪怕第一版只支持 `status / jog / stop / relay`，也比继续扩展本地 Web Serial 更稳。

### Issue #029 — 缺少配方、动作队列和多设备编排基础设施

**优先级**：中
**类型**：功能
**涉及文件**：`README.md`、`docs/architecture.md`、`firmware/motor_control/motor_control.ino`

**描述**：
当前系统只支持手动点动、连续移动和少量探测页面，还没有“配方”这一层抽象。对智能旋涂仪而言，真正需要的是可复用的动作序列：回零、到位、夹持、放液、旋涂、等待、记录、复位。现在这些能力分散成多个手工页面，无法组成一次可复现的实验流程。

**为什么重要**：
没有队列和配方，项目就停留在“可调试硬件”而不是“可执行实验”。越晚定义流程原语，后面越容易把设备控制写成一堆互相耦合的脚本。

**建议方案**：
定义最小任务模型，例如 `home / moveAbs / relay / rs485 / dwell / assert / record`，并支持 dry-run。先让树莓派服务按队列执行这些原语，再在 UI 层做配方编辑和启动。

### Issue #030 — 缺少实验记录、设备事件和参数的持久化

**优先级**：低
**类型**：工程
**涉及文件**：`web_control/index.html`、`web_control/homing_test.html`、`web_control/gripper.html`、`docs/architecture.md`

**描述**：
目前日志基本都是页面里的临时 DOM 文本，关页即失；夹爪页虽然能导出日志，但也只是人工触发的文本快照。系统还没有把实验参数、报警、回零结果、串口故障、操作动作按“实验运行”维度保存下来。对实验设备来说，这部分迟早要补。

**为什么重要**：
没有持久记录，就很难复盘“这次实验为什么失败”或“哪次回零后坐标开始飘”。等设备真正用于实验时，这会变成数据可信度问题，而不是单纯的开发体验问题。

**建议方案**：
在 host service 层按 run 维度落盘 JSON 或 SQLite，至少记录时间戳、配方参数、动作序列、状态快照、报警和异常。前端日志保留为调试视图，不再承担正式记录职责。
