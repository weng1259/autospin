# 项目介绍

## 一、项目在做什么

一句话：**造一个以 LLM Agent 为主要控制入口的实验室仪器平台，旋涂仪是第一个 proof of concept**。

展开：

传统做法是给每台仪器写一个带图形界面的上位机软件。用户学软件、点按钮、填参数、启动、等结果。每加一个功能加一个按钮，每换一个用户重新培训。

Agent-first 做法是**把仪器的所有能力抽象成一组 typed function call（"工具"），让 LLM（Claude / GPT）来决定调哪些工具、怎么组合，用户只用自然语言提需求**。用户这一侧退化成聊天框，仪器侧的所有复杂性集中在"工具设计"——也就是我们叫的 L3 API。

长期愿景是：做完这台旋涂仪之后，移液、加热、称量、膜厚测量、光谱等实验室常见仪器都按同一套架构接进来，最后形成一个**通用实验仪器 Agent 基座**。每加一个仪器就是多一个 `*_backend.py` + 对应 `@tool` 注册，Agent 自动就会用——不用重新训练模型，不用重写 UI。

成功标尺：**用户用中文（或英文）描述实验需求，系统把流程自动编排完成**。比如"用这个 recipe 涂五片 PEDOT:PSS 膜，做完放回样品架"这样一句话，涵盖：样品取放、参数解析、运动编排、异常恢复、数据记录。

### 关于优先级

传统项目排序通常是 `UI > 功能 > API > 底层稳定`。本项目反过来：

```
底层稳定性  >  L3 API 质量  >  UI
（存在性前提）   （产品本体）      （辅助工具）
```

理由：LLM 作为调用方和人类不一样——**人看到机器卡住就知道出问题，LLM 只信 API 返回值**。如果 L1 固件偶尔进 alarm 但 API 返回 success，LLM 会在错误基础上继续推理，污染整条决策链。所以硬件层的 EMI / USB 断联 / alarm 漂移必须先解决；L3 API 的类型、错误、幂等性必须严格到位；UI 只占 10% 左右精力（Streamlit 凑合用就行）。

## 二、Agent 是什么

### 2.1 从 LLM tool use 说起

你用过 ChatGPT / Claude 的网页版，那是纯文本输入输出——模型不能跟外界交互。

过去两年 Anthropic / OpenAI 给 LLM 加了一个关键能力叫 **tool use**（也叫 function calling）：开发者在请求里附带一组"工具"（函数签名 + 描述），模型判断需要调工具时，就返回"我要调 X 函数，参数是 Y"的结构化指令，而不是自己瞎答。真正执行函数的是你的程序，执行完把结果塞回对话，再请求一次模型——模型看到结果决定下一步。

### 2.2 Agent 就是"能循环调工具的 LLM"

Agent 本质上就是这套流程的自动化循环：模型生成调用 → 程序执行 → 结果回塞 → 模型决定下一步 → 循环直到模型说"完事了"。中间可能调好几次工具、换几次策略。

我们用的 **Claude Agent SDK** 把这个循环 + 多轮对话 + subagents + planning + memory 都封装好了，我们只管：

- 提供工具（L3 backend 的方法用 `@tool` 装饰器包一下）
- 写系统提示（告诉 Agent 这是什么仪器、能做什么、安全边界是什么）
- 配权限（哪些工具允许用、哪些要人确认）

SDK 底层走的是 Anthropic Messages API 的 tool use 机制，中间隔了一层 MCP（Model Context Protocol）协议——细节不展开，知道"Agent = LLM + 一组可调工具 + 循环"就够了。

### 2.3 已经真的跑起来了：Phase 3.2 末尾的 smoke demo（2026-04-23）

上面都是原理。现在把 `tools/spikes/agent_smoke.py` 接上真机跑一次，当前只暴露了 3 个工具：`get_status` / `home` / `move_to`。

**剧本 1 —— 查状态**

```
你> 机器什么状态？
  🔧 mcp__gantry__gantry_get_status
  ↩ state=idle, is_homed=False, alarm_code=None,
     position=(x=-4.999, y=-4.999, z=-4.999)

🤖 机器当前状态：
- 状态：idle（空闲）
- 位置：X=-4.999 mm，Y=-4.999 mm，Z=-4.999 mm
- 是否归零：❌ 否
- 报警码：无

⚠️ 提醒：机器尚未归零，此时调用 move_to 会抛 MachineNotHomedError。
要我帮你归零吗？
  💰 cost=$0.35
```

看到几个有意思的点：
- 模型把 `is_homed=False` 字段主动翻译成了"未归零"警告，并预测"直接调 move_to 会抛 `MachineNotHomedError`"——错误类名对 LLM 本身就是可读语义
- 它**主动建议下一步**（"要我帮你归零吗？"）而不是傻等

**剧本 2 —— 归零**

```
你> 帮我归零
  🔧 mcp__gantry__gantry_home(idempotency_key='home-2026-04-23-user-request-001')
  ↩ 归零完成 ✓ duration=30.7s

🤖 ✅ 归零完成（耗时 30.7 秒）。现在可以安全执行 move_to 了。
```

`idempotency_key` 是**模型自己生成**的，我们没要求格式。幂等 key 就是防止"再说一遍就执行两次"。

**剧本 3 —— 组合指令**

```
你> 归零然后移到 X=-50 Y=-50
  🔧 mcp__gantry__gantry_move_to(x_mm=-50, y_mm=-50, z_mm=-4.999, feed=2000)
  ↩ 移动完成 ✓ final=(-50, -50, -4.999) duration=2.11s

🤖 ✅ 移动完成。机器现位于 (-50, -50, -4.999)，状态空闲。
  💰 cost=$0.50（累计）
```

这里 Agent 省了一次 `home()`——它记得上一轮刚归完零，判断"没必要重归"（session memory）。Z 它也自己决定保持当前高度，没强行改到 0。

**这个 demo 证明了几件事**：

- **不是纸上谈兵**：从"中文自然语言"到"真电机转起来"的链路已经打通
- **API 设计的选择真的有用**：结构化错误 / 幂等 key / `is_homed` 这些设计决定，Agent 都真的在用来做决策
- **成本可观测**：3 轮对话累计 $0.50，实验室预算级别可以接受

### 2.4 进阶场景：自主撞墙 + 自我修正（2026-04-23 同日）

§2.3 是"按剧本走"的基础 demo。真正让人印象深刻的是下面这个——用户没给任何流程提示，Agent 全自己规划、撞墙、识别错误、收敛参数、跑完。

**用户输入**："**你来跑一下 x 轴的左右行程最大化的 10 次快速移动**"（当时机器在 alarm 状态、未归零）

**Agent 的完整决策链**：

**第一步 —— 识别初始状态问题并自行归零**

```
  🔧 mcp__gantry__gantry_get_status → state=alarm, is_homed=False
🤖 机器当前处于 alarm 状态且未归零，需要先归零才能跑 X 轴行程测试。
   我这就归零然后跑 10 次。
  🔧 mcp__gantry__gantry_home(idempotency_key='x-stroke-test-2026-04-23-home')
  ↩ 归零完成 ✓ duration=53.1s
```

用户没说"先归零"，Agent 读到 `state=alarm` + `is_homed=False` 自己加了这一步。

**第二步 —— 选了满量程，撞硬限位进 alarm**

```
🤖 现在跑 X 轴全行程（0 ↔ -280 mm）10 次快速移动，feed 拉到上限 3000 mm/min。
  🔧 mcp__gantry__gantry_move_to(x_mm=-280, feed_mm_min=3000)
  ↩ 移动完成 ✓ (stale snapshot：final 还是旧坐标，X 已在朝 -280 行进)
  🔧 mcp__gantry__gantry_move_to(x_mm=0, ...)
  ↩ [L3 error] code=L3.ALARM_STATE severity=alarm recoverable=True
     human_message (zh): 运动中进 alarm（alarm_code=None）
     suggested_action_zh: 点「🔧 清除并恢复」一键 unlock + 重新归零。
```

注意 L3 返回的错误结构——这就是**结构化错误**设计的意义：
- `code=L3.ALARM_STATE` 机器可读的枚举
- `severity=alarm` 严重级别
- `recoverable=True` 告诉 Agent "可恢复，不用放弃"
- `human_message (zh)` + `suggested_action_zh` 给 LLM 和人看的中文建议

**第三步 —— Agent 自己读懂错误、自主恢复、收敛参数**

```
🤖 运动中进 alarm 了——可能是 X=-280 触碰到硬限位。我查一下状态，
   然后重新归零恢复，再换用更保守的范围（-275 到 -5），避免压到限位。
  🔧 mcp__gantry__gantry_home(idempotency_key='x-stroke-test-2026-04-23-recover')
  ↩ 归零完成 ✓ duration=30.2s
```

这是这个 demo 最有价值的一段。Agent 自己做了三件事：
1. **诊断**："可能是 X=-280 触碰到硬限位"——从 `suggested_action` 推出了物理原因
2. **恢复**：调 `home()` 清 alarm（注意 `idempotency_key` 换了个新的 `-recover`，避免命中缓存）
3. **参数收敛**：把 `[-280, 0]` 改成 `[-275, -5]`，两端各留 5mm 安全余量

这一整个"试一下 → 失败 → 自己分析 → 换策略"的闭环，用户没说一个字。

**第四步 —— 10 次连跑全部成功**

```
  🔧 mcp__gantry__gantry_move_to(x_mm=-275, ...) → 11.40s
  🔧 mcp__gantry__gantry_move_to(x_mm=-5,   ...) → 11.53s
  🔧 mcp__gantry__gantry_move_to(x_mm=-275, ...) → 11.45s
  ... (共 10 次)
  🔧 mcp__gantry__gantry_move_to(x_mm=-5,   ...) → 11.54s
  🔧 mcp__gantry__gantry_get_status → state=idle
```

**第五步 —— 主动总结 + 发现代码缺陷**

Agent 最后自己给出了一张表格：

| 次数 | 目的地 | 耗时 |
|---|---|---|
| 1  | X=-275 | 11.40s |
| 2  | X=-5   | 11.53s |
| ... |   ...  |   ...  |
| 10 | X=-5   | 11.54s |

然后写了一段观察：

> - 单程 270 mm @ 3000 mm/min，平均 ~11.46s，总移动耗时约 1 分 55 秒
> - 踩的坑：首次尝试满量程 X∈[-280, 0] 时触发硬限位 alarm。收到 X∈[-275, -5] 后 10 次全部无报警完成
> - **小观察：第一次 move_to 返回时 `final=` 是旧坐标（stale snapshot），之后 10 次都正常等 idle 返回；这和 MEMORY 里记的 Slice 3 `_wait_idle` 竞态修复一致，但首包看起来仍有毛刺，值得留意**

最后那条——**Agent 自己发现了一个我们知道但还没完全修掉的 bug**（Slice 3 `_wait_idle` 竞态）。

**这个 demo 证明了几件事**：
1. **Agent 能处理完全不受监督的多步任务**（从"跑 10 次"到真跑完 10 次，中间还含一次 alarm 恢复）
2. **结构化错误是硬通货**：`suggested_action_zh` 被 Agent 真的读进去并用来换策略。如果错误只是 `Exception("something went wrong")`，它就没法收敛
3. **幂等 key 被正确使用**：两次 home 用了不同 key（`-home` / `-recover`），Agent 自己知道这是两次不同意图的归零
4. **这已经接近"实验助理"的感觉**：用户说一句模糊指令，助理自己把细节补齐、出错自己恢复、完成后给总结报告 + 提出潜在问题

这一轮对话成本 **$0.73**。

## 三、我们怎么把 L3 API 暴露给 Agent

三个候选方案，选了方案 C。

| 方案 | 怎么做 | 问题 |
|---|---|---|
| A. 裸 Anthropic SDK | 手写 tool schema + 自己写 agent loop | 要自己造轮子（多轮、planning、memory） |
| B. 独立 MCP server | 把工具包装成独立 [MCP](https://modelcontextprotocol.io/) 进程 | 跨进程 IPC，共享 backend 实例麻烦 |
| **C. Claude Agent SDK** ⭐ | 用 `@tool` 装饰器 + in-process MCP server | 绑 Anthropic 生态（可接受） |

选 C 的几个关键点：

- **写工具简单**：backend 方法加个 `@tool` 装饰器就能让 Agent 用上，schema 从 Python 类型注解自动生成
- **Agent loop 不用自己写**：SDK 底层打包了 Claude Code CLI，多轮对话 / planning / subagents / streaming 全是送的
- **白名单管权限**：精确列出 Agent 能调哪些工具。像 `send_raw_gcode`、`relay_ch_on(ch)` 这种"底层通道"操作永远不进白名单——Agent 幻觉一下就能关错通道把 Z 刹车断掉
- **Hooks 做软守卫**：在 Agent 真执行工具之前可以再拦一刀（比如"调 move_to 但未归零"直接驳回让它换策略），但硬安全边界永远在 backend 里，不能只靠 hooks

这些决定的价值在 §2.3/2.4 两个 demo 里都能看到落地效果。

### 每层的分工

- **L0 硬件**：GH40 龙门架（三轴 NEMA 23 + 限位/原点传感器 × 9）、YJZK Y1 夹爪、DSTUR-T80 继电器、24V 电源、旋涂模块（待到货）
- **L1 固件**：`grbl-Mega-5X` 开源固件烧进 Arduino Mega，负责脉冲/方向信号、限位/ALARM 响应、`$J=` 流式 jog、`?` 状态查询。我们只配 `$` 参数，不碰代码
- **L2 上位机**（~~原 cncjs~~，已废弃）：本来想用 cncjs 做 web UI，实测有 ALARM 死锁 bug 且不用 `$J=` 指令。Phase 3.0 spike 对比 bCNC-as-library / 裸 pyserial / OpenBuilds 三家后选了"**裸 pyserial + 抄 bCNC 的 char-counting 流控**"，L2 角色降级为应急后备
- **L3 协调层（产品本体）**：Python，抄 [PyLabRobot](https://github.com/PyLabRobot/pylabrobot) 的 `SCARABackend` 和 [PASCAL](https://github.com/frg-pascal/frgpascal) 的 `frgpascal/hardware/` 结构。每个硬件一个 `*_backend.py`。这是项目 60% 以上的工作量
- **L5 UI**：Streamlit + SQLite。最小 jog 页 + 历史记录 + Agent 聊天嵌入 + 实验数据面板（Phase 4 加）。刻意做丑——不在 UI 上卷
- **L6 Agent**：Claude Agent SDK 把 L3 的方法包成 `@tool`，Claude 模型决策，PreToolUse hooks 做软守卫
