# ADR-003：Agent-first 实验室自动化愿景与优先级重排

- **日期**：2026-04-20
- **状态**：已决定，指导所有后续工作
- **决策人**：Kevin
- **影响范围**：全栈——从硬件稳定性验收到 L5 UI 定位，所有后续 ADR 和 Phase 均以本 ADR 为前提
- **关联**：[ADR-001](ADR-001-migrate-to-grbl-stack.md)（栈选型）· [ADR-002](ADR-002-replace-cncjs.md)（L2 重选）· [ADR-004](ADR-004-l3-api-design-principles.md)（L3 API 规范）

## 背景

前序两份 ADR 解决的是"如何让机器稳定运行"的问题（选 grbl、选 L2 上位机）。2026-04-20 做 cncjs 稳定性诊断时，话题被拉回到更根本的问题——**这台机器到底是为谁、为什么场景设计的**？

在此之前项目默认的场景是"实验科学家坐在机器前，通过 UI 点动、提交 recipe、看结果"。UI 是核心交付物。

本 ADR 记录的是对这个默认假设的**推翻**。

## 愿景

**本项目是整个实验室智能仪器重构的第一台**。长期目标不是"造一台旋涂仪"，是**造一套以 Agent（LLM 智能体）为主要控制入口的实验仪器平台**。旋涂仪是 proof of concept，后续会横向扩展到移液、加热、称量、光谱等全部常见实验操作。

成功标尺：**一个不懂具体实验流程的新手，只要能用自然语言描述他需要做什么，系统就能把实验完美完成**。

> 类比：用户不需要懂 MySQL 就能让 ChatGPT 帮他分析数据；类似地，用户不需要懂"先校准 Z 再降速旋涂 30 秒"的细节，只要说"我要做一个 PEDOT:PSS 的薄膜"。

## 优先级重排（本 ADR 的核心）

原项目的重要性排序：

```
UI/UX  >  功能完整性  >  API 设计  >  底层稳定性
```

Agent-first 架构下的重要性排序：

```
底层稳定性  >  API 质量  >  UI
（存在性前提）   （产品本体）   （辅助工具，必须有但非核心）
```

三条根本理由：

### 1. 底层稳定性是 Agent 世界里的"存在性前提"

Agent 作为调用方和人的本质区别：**人能看到机器不动了就知道出错；Agent 只能信 API 返回值**。如果 L1 grbl 会偶尔进 alarm 但 API 返回 success，Agent 会在错误基础上继续做决策，污染整条推理链——比人类操作下显式报错糟糕得多。所以：

- 任何未被 API 明示的失败都是灾难级 bug
- 硬件层偷偷的 EMI / USB 断联 / alarm 漂移必须先于任何上层设计解决
- 今天的 `tools/grbl_stability_test.py` 不是"一次性诊断工具"，是**系统正式组件**，每次底层变动都要回归跑

### 2. API 才是产品，不是 UI

用户（和未来的 Agent）和系统交互的合同是 L3 的 API，不是任何 UI 的按钮布局。UI 只是 API 的一种具象化呈现——而且在 Agent-first 世界里，是**次要**的呈现方式。

这意味着：
- L3 API 要按"LLM tool schema"的标准设计（严格类型、结构化错误、可观测状态、幂等性、硬编码安全边界），**而不是**按"开发者方便写"的标准
- API 必须能被人类和 Agent **同等使用**——任何"人类才懂的潜规则"都是泄漏的抽象
- API 设计先于 UI 设计。UI 是 API 的 consumer，不是反过来

详细规范见 [ADR-004](ADR-004-l3-api-design-principles.md)。

### 3. UI 降级为"必要但非核心的辅助工具"

UI 的价值从"主要交互通道"降级到**三个窄场景**：

| 场景 | 占比 | UI 形态 |
|---|---|---|
| Agent 调不动了，人类要应急接管 | ~5% | OpenBuilds 或 bCNC 或自研最小 jog 页（L2 应急 UI） |
| 实验数据可视化、历史查询、recipe 编辑 | ~10% | Streamlit + SQLite（L5） |
| **Agent 作为主要入口** | **~85%** | **聊天界面 / API 调用 / 命令行**（可嵌在 L5 里） |

UI 设计的投入要按这个比例分配。不能再把"漂亮的 jog 面板"作为项目质量标志。

**对旧架构图的三点关键变更**：
1. Agent 层从"可选"提到主要入口
2. L3 从"薄协调层"升格为"产品本体"
3. L2 从"首要 UI"降级为"应急备份"——是否需要它、选哪个，反而由 L3 API 的实现路径决定（见 ADR-002 修订说明）

## 对既有 ADR 的影响

### ADR-001（grbl 栈迁移）

**核心结论不变**，但重新强调了其中两点：
- "薄 Python orchestrator" 的"薄"不再成立——L3 从 2-3 天扩成 4-5 天甚至更多，它是产品
- grbl-Mega-5X 的稳定性验收要求提高——Phase 1 当时的 "6/7 项通过" 在 Agent-first 里不够，需要补稳定性回归作为持续 CI

### ADR-002（cncjs → OpenBuilds）

**推荐结论需要修订**。原 ADR-002 按"用户 UI 体验"排序把 OpenBuilds 排第一。Agent-first 框架下评估维度变成**"L3 API 构建成本与可靠性"**，bCNC（Python 原生）或"DIY + 抄 bCNC 流控"反而可能更优。正式决定延后到 ADR-004 写完后。详见 ADR-002 末尾新增的 "2026-04-20 晚修订" 章节。

### Phase 规划

见 `migration-checklist.md` 的更新：
- Phase 2（cncjs 装机）回退为"未通过"
- Phase 3 范围重新定义为"L3 API surface v1 + Agent demo"，预算扩大
- 新增 Phase 3.5：**第一个 Agent demo**作为 Phase 3 验收标准

## 回滚条件

本 ADR 的愿景面临两种情形会被推翻：

1. **Agent 技术达不到精度要求**：例如 LLM tool-use 在实验科学场景的幻觉率 > 10%、长链路决策不可靠到不能托付样品操作。此时退回"UI-first + Agent 作 copilot"的折衷方案。
2. **项目方向转为商业化面向客户**：客户更愿意为漂亮 UI 付费而不是 API 质量。此时 UI 重新升级为第一优先级。

目前（2026-04-20）两个条件都不成立，所以本愿景执行。
